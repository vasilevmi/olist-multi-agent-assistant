# Архитектура мультиагентного ассистента Olist

## 1. Назначение

Система отвечает на бизнес-вопросы по историческим данным маркетплейса Olist.
LLM понимает запрос, выбирает специализированных агентов и объясняет результат,
но не вычисляет показатели самостоятельно. Числа получает PostgreSQL через
детерминированные репозитории и MCP-инструменты.

## 2. Полный путь запроса

```text
Web UI / CLI
    ↓
HTTP API
    ↓
TracedInvestigateQuestion ─────────────→ Langfuse
    ↓
InvestigateQuestion
    ↓
LangChain Orchestrator
    ├── ask_sales_agent ───→ Sales Agent ────┐
    ├── ask_seller_agent ──→ Seller Agent ───┤
    ├── ask_delivery_agent → Delivery Agent ─┤
    └── ask_reviews_agent ─→ Reviews Agent ──┤
                                              ↓
                                  LangChain MCP adapter
                                              ↓
                                      FastMCP tools
                                              ↓
                                Application Use Cases
                                              ↓
                              Repositories → PostgreSQL
                                              ↓
                                           Evidence
                                              ↓
                                  LangChain Evidence Critic
                                              ↓
                         Ответ + факты + гипотезы + confidence
```

Используется паттерн **subagents as tools**. Orchestrator видит четыре
инструмента делегирования, а не весь набор SQL-операций. Каждый специализированный
агент получает только относящиеся к его области MCP-инструменты.

## 3. Слои проекта

### `domain/`

Содержит бизнес-сущности и абстракции репозиториев: заказы, продавцов, товары,
доставки, отзывы, `Investigation`, `Evidence` и `Finding`. Домен не импортирует
LangChain, MCP, PostgreSQL или HTTP.

### `application/`

Содержит сценарии использования. Use Case проверяет входные параметры,
обращается к абстракции Repository и возвращает доменный результат.
`application/investigate/use_cases.py` дополнительно собирает сообщения агентов
в единый объект `Investigation` и передаёт Evidence критику.

### `infrastructure/postgres/`

Содержит SQL и реализации доменных репозиториев. Только этот слой знает схему
таблиц PostgreSQL и преобразует строки базы в доменные сущности.

### `infrastructure/mcp/`

FastMCP-серверы публикуют разрешённые бизнес-операции как инструменты. Они
вызывают Application Use Cases, преобразуют доменный результат в сериализуемый
ответ и не содержат основную SQL-логику.

`infrastructure/mcp/langchain_client.py` запускает локальные MCP-серверы через
`stdio` и преобразует их инструменты в `BaseTool`, понятные LangChain.

### `infrastructure/agents/`

- **Orchestrator** выбирает нужную предметную область и делегирует задачу;
- **Sales Agent** работает с продажами, заказами, товарами и категориями;
- **Seller Agent** отвечает за продавцов, местоположение и ассортимент;
- **Delivery Agent** анализирует сроки, задержки и регионы;
- **Reviews Agent** анализирует оценки, отзывы и клиентский опыт;
- **Evidence Critic** проверяет Evidence и создаёт структурированный ответ.

Агенты создаются функцией `langchain.agents.create_agent`. Специализированные
агенты представлены Orchestrator как инструменты `ask_*_agent`.

### `infrastructure/llm/`

`create_chat_model()` создаёт `ChatOpenAI` с адресом, ключом и названием модели
из `.env`. Подходит любой провайдер с OpenAI-совместимым API.

### `infrastructure/observability/`

`TracedInvestigateQuestion` создаёт верхнеуровневую трассу. Langfuse callback
получает вложенные вызовы модели, агентов и инструментов через `RunnableConfig`.
Трассировки отправляются на сервер, указанный в настройках Langfuse.

### `interfaces/`

HTTP API принимает вопрос, ограниченную историю и `session_id`. Web UI показывает
пользовательский ответ, а шаги, Evidence, гипотезы и технические сведения прячет
в раскрываемый блок.

### `evaluation/`

DeepEval запускает приложение на контрольном наборе `cases.json`. Адаптер
преобразует `Investigation` в `LLMTestCase`, а LLM-судья оценивает релевантность,
верность Evidence, бизнес-корректность и полноту исследования.

## 4. Выполнение одного исследования

1. API создаёт runtime в `infrastructure/bootstrap.py`.
2. Bootstrap создаёт модель, четырех специализированных агентов, Orchestrator и Critic.
3. Orchestrator получает вопрос и при необходимости историю диалога.
4. Orchestrator вызывает один или несколько инструментов делегирования.
5. Специализированный агент самостоятельно выбирает минимально необходимые MCP-tools.
6. MCP вызывает Use Case, Repository выполняет SQL и возвращает результат.
7. Результаты `ToolMessage` преобразуются в шаги и Evidence.
8. Ошибка отдельного инструмента сохраняется как ограничение; успешные Evidence не теряются.
9. Critic получает только вопрос, Evidence и ограничения.
10. Pydantic-схема `CriticResponse` проверяет структуру фактов и гипотез.
11. API возвращает ответ и технические детали интерфейсу.

## 5. Evidence и выводы

**Evidence** — результат конкретного MCP-инструмента с источником, названием
инструмента, данными и уникальным `evidence_id`.

**Finding** — утверждение Critic, содержащее ссылки на Evidence, уровень
уверенности и признак гипотезы.

- `high` — значение прямо присутствует в Evidence;
- `medium` — вывод получен сравнением подтверждённых данных;
- `low` — осторожная гипотеза без прямого доказательства причинности.

Факт без ссылки на Evidence не принимается, а гипотеза не может иметь
`confidence=high`.

## 6. История диалога

Браузер передаёт последние 10 сообщений вместе с новым вопросом. `session_id`
связывает запросы в Langfuse, но постоянного серверного хранилища сообщений пока
нет. После обновления страницы локальная история теряется.

## 7. Почему выбран LangChain

- предоставляет стандартный цикл `model → tool → result → model`;
- поддерживает асинхронные `ainvoke` и единый формат сообщений;
- умеет работать со структурированным Pydantic-ответом;
- интегрируется с MCP-адаптерами и callback-трассировкой;
- уменьшает объём самописного кода оркестрации.

Цена подхода — дополнительные LLM-вызовы, зависимость от версий библиотек и
меньшая детерминированность маршрутизации по сравнению с ручным кодом.

## 8. Ограничения

- runtime и MCP-сессии пока создаются заново для каждого HTTP-запроса;
- `RunMetrics` сейчас надёжно измеряет время, а детализация вызовов находится в Langfuse;
- история не сохраняется после закрытия страницы;
- результат зависит от доступности внешней LLM и корпоративного VPN;
- отзывы относятся ко всему заказу и не всегда однозначно к одному продавцу;
- в датасете нет полной информации о возвратах, прибыли и себестоимости.
