# Архитектура мультиагентного аналитического ассистента Olist

## 1. Назначение системы

Проект представляет собой аналитического ассистента для данных бразильского
маркетплейса Olist. Пользователь задаёт бизнес-вопрос на естественном языке,
например: «Почему у продавца низкий рейтинг?» или «Какие категории приносят
наибольшую выручку?». Система определяет, какие данные нужны для ответа,
вызывает подходящие инструменты, получает факты из PostgreSQL и формирует
ответ, основанный на этих фактах.

Главная идея проекта: языковая модель не получает прямой доступ к базе и не
должна придумывать показатели. Числа извлекаются детерминированными
SQL-запросами, а LLM используется для планирования исследования, выбора
инструментов и объяснения полученных результатов.

## 2. Общая схема

```text
Пользователь
    ↓
Web UI → HTTP API
    ↓
InvestigateQuestion
    ↓
LLM Orchestrator
    ↓
MultiAgentExecutor
    ├── Sales Agent
    ├── Seller Agent
    ├── Delivery Agent
    └── Reviews Agent
              ↓
         MCP-инструмент
              ↓
           Use Case
              ↓
     Repository → PostgreSQL
              ↓
           Evidence
              ↓
     Critic / Evidence Agent
              ↓
Ответ + факты + гипотезы + confidence
```

Система построена как управляемый цикл исследования. Orchestrator выбирает не
весь план сразу, а один следующий шаг. После выполнения шага он получает новые
Evidence и снова решает, достаточно ли данных или нужен ещё один инструмент.

## 3. Слои проекта

### `domain/` — предметная область

Доменный слой содержит бизнес-сущности и контракты репозиториев. Например:

- заказ и позиция заказа;
- показатели продаж продавца;
- статистика доставки;
- отзыв и статистика оценок;
- продавец и его ассортимент;
- исследование, шаг, Evidence и Finding.

Домен не знает о PostgreSQL, HTTP, MCP или конкретной LLM. Благодаря этому
бизнес-модели не зависят от внешних технологий.

### `application/` — сценарии использования

Use Case описывает одну операцию приложения: получить продажи продавца,
найти заказ, рассчитать статистику доставки или выполнить исследование.

Use Case:

1. принимает входные параметры;
2. проверяет их;
3. вызывает интерфейс Repository;
4. возвращает доменную сущность.

Здесь же находятся порты `InvestigationPlanner`, `AgentExecutor` и
`InvestigationAnalyst`. Порт — это контракт, которому должна соответствовать
конкретная реализация планировщика, исполнителя или аналитика.

### `infrastructure/postgres/` — доступ к данным

В этом слое находятся реализации репозиториев и SQL-запросы. Репозиторий
получает данные из таблиц схемы `raw`, выполняет объединения и агрегаты, а затем
преобразует строки PostgreSQL в доменные сущности.

Например, `PostgresSalesRepository` знает названия таблиц и колонок, а доменный
`SalesRepository` определяет только то, какие операции нужны приложению.

### `infrastructure/mcp/` — инструменты системы

MCP-инструменты образуют контролируемый набор операций, которые разрешено
вызывать агентам. Они не содержат основной SQL-логики, а связывают внешний
вызов с соответствующим Use Case.

Типичный путь одного инструмента:

```text
get_seller_sales(seller_id)
    → GetSellerSales.execute(...)
    → SalesRepository.get_seller_sales(...)
    → SQL
    → SellerSalesSummary
    → JSON-результат MCP
```

Разделение MCP и Repository важно: инструмент описывает доступную возможность
системы, а Repository отвечает за способ получения данных.

### `infrastructure/agents/` — мультиагентная система

Агенты специализируются на разных группах задач:

- **Orchestrator** понимает вопрос, выбирает следующий шаг, агента и MCP-tool;
- **Sales Agent** работает с заказами, выручкой, товарами и категориями;
- **Seller Agent** анализирует продавца и его ассортимент;
- **Delivery Agent** отвечает за сроки, задержки и регионы доставки;
- **Reviews Agent** работает с рейтингами, отзывами и клиентским опытом;
- **Critic / Evidence Agent** проверяет собранные Evidence и формирует ответ.

Специализация уменьшает размер задачи для каждого агента и ограничивает набор
доступных ему инструментов. Агент не выполняет произвольный SQL: он может
вызвать только зарегистрированную Python-функцию с проверенными аргументами.

### `infrastructure/execution/` — маршрутизация

`MultiAgentExecutor` получает имя агента от Orchestrator, находит его в реестре
и передаёт ему описание задачи, имя инструмента и аргументы. Сам Executor не
принимает бизнес-решений — он только маршрутизирует вызов.

### `infrastructure/llm/` — подключение модели

`OpenAICompatibleClient` скрывает особенности конкретного поставщика LLM.
Провайдера, модель и ключ можно менять через `.env`, не изменяя Orchestrator и
остальных агентов. Клиент запрашивает структурированный JSON и обрабатывает
несколько вариантов поддержки `response_format`.

### `interfaces/` — взаимодействие с пользователем

- `interfaces/api/` предоставляет HTTP API;
- `interfaces/web/` содержит браузерный интерфейс.

Пользователь видит понятный ответ, основные факторы и возможные следующие
проверки. Шаги агентов, MCP-инструменты, Evidence, гипотезы и метрики доступны
отдельно в блоке «Технические детали».

## 4. Полный путь пользовательского запроса

1. Web UI отправляет вопрос и последние сообщения диалога в HTTP API.
2. API создаёт runtime через `infrastructure/bootstrap.py`.
3. `InvestigateQuestion` создаёт объект исследования и запускает цикл.
4. Orchestrator получает вопрос, уже выполненные шаги и Evidence.
5. Orchestrator возвращает решение: выполнить следующий шаг или завершить
   сбор данных.
6. `MultiAgentExecutor` направляет шаг выбранному специализированному агенту.
7. Агент проверяет выбор и вызывает зарегистрированный MCP-инструмент.
8. MCP-инструмент вызывает Use Case, Repository выполняет SQL в PostgreSQL.
9. Результат сохраняется как Evidence с уникальным `evidence_id`.
10. Цикл повторяется, пока данных не станет достаточно или не будет достигнут
    установленный предел шагов.
11. Critic получает вопрос, Evidence и известные ограничения исследования.
12. Critic формирует факты, гипотезы, уровни уверенности и итоговый ответ.
13. API сериализует результат, а Web UI показывает его пользователю.

## 5. Evidence, факты и гипотезы

**Evidence** — неизменённый результат конкретного MCP-инструмента. Он содержит:

- уникальный идентификатор;
- источник — имя агента;
- имя инструмента;
- полученные данные;
- время получения.

**Finding** — сформулированный вывод. Он содержит ссылки на `evidence_id`,
уровень уверенности и признак гипотезы.

Используются три уровня confidence:

- `high` — значение прямо присутствует в Evidence;
- `medium` — вывод получен простым сравнением нескольких Evidence;
- `low` — предположение, для которого нет прямого доказательства причинности.

Такое разделение позволяет показать, откуда взялся каждый факт, и не выдавать
возможное объяснение за доказанную причину.

## 6. Обработка ошибок

Решение LLM считается недоверенным вводом и проверяется перед выполнением.
Проверяются имя агента, доступность инструмента, формат аргументов и повторение
одинаковых шагов.

Если отдельный инструмент завершается с ошибкой:

1. шаг получает статус `failed` и сохраняет текст ошибки;
2. уже полученные Evidence не удаляются;
3. Orchestrator может выбрать другой способ исследования;
4. если другого способа нет, Critic отвечает по доступным данным и указывает
   ограничение.

Всё исследование завершается ошибкой только тогда, когда получить достаточный
и достоверный ответ действительно невозможно, например отсутствует соединение
с базой или не было получено ни одного Evidence. Это лучше, чем скрывать сбой
или позволять модели выдумать недостающие значения.

## 7. История диалога

История сейчас хранится в памяти открытой страницы браузера. В новый запрос
передаются последние 10 сообщений, поэтому пользователь может продолжить
диалог словами «этот продавец» или «сравни его со средним».

История очищается при обновлении страницы, закрытии вкладки или нажатии кнопки
«Новый диалог». Это осознанное ограничение текущего прототипа. Для постоянного
хранения потребуются таблицы диалогов и сообщений в PostgreSQL.

## 8. Сборка приложения

`infrastructure/bootstrap.py` является composition root — местом, где создаются
и связываются конкретные реализации:

```text
LLM client
    → Orchestrator
    → специализированные агенты
    → MultiAgentExecutor
    → Critic
    → InvestigateQuestion
```

Такой подход сохраняет зависимости явными и позволяет заменить LLM-клиент,
репозиторий или агента без изменения доменной модели.

## 9. Docker

`compose.yaml` описывает три сервиса:

- `db` — PostgreSQL из готового образа;
- `loader` — одноразовая загрузка CSV-файлов в базу;
- `app` — API и Web UI проекта.

`app` и `loader` используют один Dockerfile, но запускают разные команды.
Постоянные данные PostgreSQL сохраняются в именованном volume
`postgres_data`.

## 10. Evaluation и наблюдаемость

В `evaluation/cases.json` находится контрольный набор бизнес-вопросов.
Детерминированные кейсы сравниваются с заранее рассчитанными значениями, а
исследовательские проверяются по полноте Evidence, выбору инструментов и
структуре ответа.

Основные метрики:

- доля успешно пройденных кейсов;
- фактическая точность;
- покрытие выводов Evidence;
- ошибки выбора инструментов;
- количество MCP- и LLM-вызовов;
- время выполнения.

Во время обычного запроса `RunMetrics` считает вызовы модели, решения
Orchestrator, инструменты и общую продолжительность. Метрики позволяют
оценивать не только правильность, но и стоимость исследования.

## 11. Почему выбрана такая архитектура

- **DDD** отделяет бизнес-модели от PostgreSQL и внешних интерфейсов.
- **Repository** изолирует SQL и позволяет заменить хранилище.
- **Use Case** фиксирует одну понятную операцию приложения.
- **MCP** предоставляет агентам ограниченный и проверяемый набор возможностей.
- **Специализированные агенты** разделяют большую задачу по предметным областям.
- **Orchestrator** строит план динамически, исходя из вопроса и уже полученных
  результатов.
- **Evidence и Critic** снижают риск неподтверждённых утверждений.
- **Evaluation** делает проверку качества воспроизводимой.
- **Docker** упрощает передачу и запуск проекта на другом компьютере.

## 12. Ограничения

- качество планирования и формулировки ответа зависит от выбранной LLM;
- отзывы относятся ко всему заказу и не всегда однозначно к одному продавцу;
- датасет исторический, поэтому система не доказывает текущую активность;
- в исходных данных отсутствуют некоторые бизнес-показатели, например
  себестоимость, прибыль и полноценные данные о возвратах;
- история диалога пока не сохраняется после обновления страницы;
- внешняя LLM и корпоративный API требуют доступного сетевого соединения.
