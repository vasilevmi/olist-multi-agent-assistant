# Памятка по метрикам evaluation

Эти метрики показывают не только то, правильно ли система ответила, но и где
именно появилась ошибка: при выборе инструмента, получении фактов или создании
итогового ответа.

Значения от `0` до `1` можно читать как проценты:

- `1.0` — 100%;
- `0.8` — 80%;
- `0.25` — 25%;
- `0.0` — 0%.

## Когда один кейс считается успешным

Кейс получает `passed: true`, только если одновременно:

1. Исследование завершилось без ошибки.
2. Orchestrator выбрал все обязательные инструменты.
3. Не были вызваны запрещённые для кейса инструменты.
4. Все заранее заданные проверки фактов прошли.
5. Выводы ссылаются на реально полученные Evidence.
6. Ответ содержит краткий вывод, основные факторы и заключение.

Если хотя бы одно условие не выполнено, кейс получает `passed: false`.

## Case success rate

Показывает, какая часть контрольных вопросов полностью пройдена.

Формула:

```text
Успешные кейсы / Все запущенные кейсы
```

Пример: из 10 кейсов прошли 8.

```text
8 / 10 = 0.8 = 80%
```

Чем ближе результат к 100%, тем лучше.

Доля ошибок по кейсам:

```text
1 - case_success_rate
```

В примере ошибки составляют `1 - 0.8 = 0.2`, то есть 20%.

## Factual accuracy

Показывает, насколько правильно система получила конкретные факты и числа.

В `cases.json` факты записываются в `assertions`. Например, тест может
проверять название первой категории и её среднюю оценку.

Формула для одного кейса:

```text
Пройденные assertions / Все assertions кейса
```

Пример: прошли 3 проверки из 4.

```text
3 / 4 = 0.75 = 75%
```

Фактическая ошибка:

```text
1 - factual_accuracy
```

Кейсы без `assertions` в расчёте этой метрики не участвуют.

## Evidence coverage

В текущем коде метрика показывает, вызваны ли обязательные инструменты,
указанные в `required_tools` и `required_tool_groups`.

Формула:

```text
Выполненные требования по инструментам / Все требования кейса
```

Пример: для анализа нужны продажи, доставка, отзывы и каталог. Система получила
данные только из трёх областей.

```text
3 / 4 = 0.75 = 75%
```

Непокрытая часть равна:

```text
1 - evidence_coverage
```

Важно: эта метрика проверяет наличие нужных результатов tools. Правильность
ссылок выводов на Evidence проверяет отдельная метрика
`evidence_grounding_rate`.

## Tool selection error rate

Показывает долю кейсов, где инструменты были выбраны неправильно.

Кейс содержит ошибку выбора, если:

- не вызван обязательный инструмент;
- не вызван ни один инструмент из обязательной группы;
- вызван инструмент из `forbidden_tools`.

Формула:

```text
Кейсы с ошибкой выбора tools / Все кейсы
```

Пример: ошибки были в 2 кейсах из 10.

```text
2 / 10 = 0.2 = 20%
```

Для этой метрики хорошо значение, близкое к 0%.

Сейчас считается число ошибочных кейсов, а не число отдельных лишних вызовов.
Даже если внутри одного кейса выбрано три неправильных инструмента, это одна
ошибка на уровне кейса.

## Evidence grounding rate

Показывает, подтверждены ли выводы результатами инструментов.

Для каждого `Finding` проверяется:

- есть ли хотя бы один `evidence_id`;
- существует ли Evidence с таким ID.

Формула:

```text
Кейсы с корректными ссылками на Evidence / Все кейсы
```

Если модель написала вывод, но не указала подтверждающий Evidence, проверка не
пройдёт.

Доля ошибок:

```text
1 - evidence_grounding_rate
```

## Structured answer rate

Показывает, вернула ли система ответ в нужной структуре.

Обязательные части:

- `short_summary` — краткий ответ;
- `main_factors` — основные факты;
- `conclusion` — итоговый вывод.

Формула:

```text
Кейсы со всеми обязательными частями / Все кейсы
```

Поле `next_checks` сохраняется в ответе, но сейчас не влияет на прохождение
этой проверки.

## Average tool calls

Показывает среднее число вызовов MCP-инструментов на один вопрос.

Формула:

```text
Все вызовы tools / Количество кейсов
```

Пример: три кейса использовали 1, 3 и 2 инструмента.

```text
(1 + 3 + 2) / 3 = 2 вызова
```

Большое значение не всегда означает ошибку: простой вопрос обычно требует один
инструмент, а сложный анализ продавца может потребовать несколько инструментов.

## LLM calls

Показывает, сколько раз система в среднем обращается к модели Groq на один
вопрос.

Для простого вопроса обычно выполняются четыре обращения:

1. Orchestrator выбирает следующий шаг.
2. Специализированный агент проверяет выбор инструмента.
3. Orchestrator решает, что данных достаточно.
4. Critic формирует итоговый ответ.

Формула:

```text
Все вызовы LLM / Количество кейсов
```

Повтор сетевого запроса после ошибки `429 Too Many Requests` сейчас не
считается отдельным логическим LLM-вызовом.

## Latency

Показывает, сколько времени система потратила на ответ.

В это время входят:

- решения Orchestrator;
- проверки специализированных агентов;
- SQL-запросы;
- работа Critic;
- сетевые задержки;
- ожидание повторного запроса после ограничения Groq.

Среднее время считается так:

```text
Суммарное время всех кейсов / Количество кейсов
```

Например, три кейса выполнялись 10, 20 и 30 секунд:

```text
(10 + 20 + 30) / 3 = 20 секунд
```

## P95 latency

P95 показывает время, быстрее которого завершились 95% запросов.

Например, `p95 = 40 секунд` означает, что примерно 95% запросов завершились за
40 секунд или быстрее, а оставшиеся 5% выполнялись дольше.

В текущем `run_evaluation.py` P95 пока не рассчитывается. Сейчас в отчёте есть
только `average_latency_seconds`.

## Как быстро понять причину провала

1. `case_success_rate` упал — один или несколько кейсов не прошли полностью.
2. `tool_selection_error_rate` вырос — Orchestrator выбрал не те tools.
3. `factual_accuracy` упал — SQL-результат или ожидаемое значение не совпали.
4. `average_evidence_coverage` упал — собраны не все обязательные данные.
5. `evidence_grounding_rate` упал — выводы не связаны с Evidence.
6. `structured_answer_rate` упал — Critic не сформировал нужные блоки ответа.
7. `average_latency_seconds` вырос — запросы, SQL или Groq стали выполняться
   дольше.

Главная итоговая метрика — `case_success_rate`. Остальные метрики нужны, чтобы
понять конкретную причину ошибки.
